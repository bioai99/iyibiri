# App v2.1 Phase 2 — Theme System + Missing Screens

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add light/dark theme system with semantic tokens, implement all 11 missing screens (Onboarding 4, NGO Profile, Membership 2, Donation 4), fix v2.1 polish items, and wire complete navigation graph.

**Architecture:** A React context-based theme provider maps semantic color keys to dark/light palette values. All components read colors from `useTheme()` hook instead of hardcoded hex values. CSS variables back the system for SSR compatibility. Missing screens follow the same inline-style pattern as Phase 1.

**Tech Stack:** Next.js 14, TypeScript, Framer Motion, Supabase, lucide-react, next/font

**Reference:** `design-system v2.1` — CHANGELOG.md, IMPLEMENTATION.md, screens_index.json, examples/theme.ts, Screens2.jsx (Onboarding), Screens3.jsx (NGO/Membership/Donation)

## Task Breakdown

### Task 1: Theme Provider + CSS Variables

**Files:**
- Create: `lib/theme.tsx` — ThemeProvider context, useTheme hook, semantic color map
- Modify: `app/globals.css` — add light mode CSS variables alongside dark
- Modify: `app/dashboard/layout.tsx` — wrap in ThemeProvider, add mode toggle capability
- Create: `components/ui/ds/theme-toggle.tsx` — simple dark/light toggle button

The theme provider exposes `{ colors, mode, setMode }` where `colors` is the semantic map. Components use `const { colors: c } = useTheme()` and reference `c.ink900`, `c.cream`, `c.gold` etc.

For SSR compatibility, also set CSS custom properties on `<html>` element so Tailwind-based parts still work.

Store mode preference in localStorage, default to 'dark'.
